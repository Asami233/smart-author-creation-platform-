# 前后端协作与代码所有权规则

## 1. 目的

本规则用于支持 Codex 与 Gemini 并行开发，核心原则是：

- 一个文件在同一阶段只有一个明确负责人。
- 前后端通过稳定契约协作，不通过互相修改代码协作。
- 所有跨界变更先形成需求，再由对应负责人实现。
- 隐私、安全和数据完整性优先于开发速度。

## 2. 角色与职责

### Gemini：前端负责人

负责：

- 页面信息架构与视觉呈现
- 桌面端响应式布局
- 富文本编辑器交互
- 章节树、侧栏、弹窗和前端状态
- 加载、空状态、错误状态和成功反馈
- 无障碍、键盘操作和前端测试
- 按已确认 API 契约完成接口调用

不负责：

- API 路由和服务端业务逻辑
- 数据库表、查询和迁移
- 登录鉴权的服务端实现
- AI 模型请求代理与密钥保护
- 服务端日志、限流、审计和权限校验

### Codex：后端负责人

负责：

- API 设计与实现
- 作品、卷、章、大纲、角色、世界观和时间线的数据模型
- 本地持久化层及未来云端数据库演进
- 历史版本、自动快照和恢复逻辑
- TXT、DOCX、PDF 导出服务
- 登录、会话、鉴权与数据隔离
- OpenAI-compatible AI 服务端适配层
- 上下文范围控制、密钥保护、限流、重试和错误映射
- 后端测试、数据库迁移和接口文档

不负责：

- 页面视觉重构
- 前端组件样式
- 未经协商替换前端状态管理方案
- 为方便后端而擅自改变用户交互

## 3. 目录所有权

| 路径 | 所有者 | 另一方权限 | 说明 |
| --- | --- | --- | --- |
| `app/api/**` | Codex | 只读 | Next.js API 路由 |
| `server/**` | Codex | 只读 | 服务、仓储、鉴权、AI 代理 |
| `db/**` | Codex | 只读 | 数据库连接与 schema |
| `drizzle/**` | Codex | 只读 | 数据库迁移 |
| `lib/server/**` | Codex | 只读 | 仅服务端使用的工具 |
| `contracts/**` | Codex | 只读 | 前后端共享的正式契约 |
| `app/**`（排除 `app/api/**`） | Gemini | 只读 | 页面、布局和前端路由 |
| `components/**` | Gemini | 只读 | 前端组件 |
| `hooks/**` | Gemini | 只读 | 浏览器端 hooks |
| `lib/client/**` | Gemini | 只读 | 前端请求封装和状态工具 |
| `public/**` | Gemini | 只读 | 静态资源 |
| `tests/backend/**` | Codex | 只读 | 后端测试 |
| `tests/frontend/**` | Gemini | 只读 | 前端测试 |

“只读”意味着可以查看和引用，但不得修改、格式化、移动、重命名或删除。

## 4. 共享文件管理

共享文件包括依赖清单、构建配置、项目说明和环境变量示例。修改流程为：

1. 提出为什么必须修改。
2. 列出会影响哪一方。
3. 由实际需要该变更的一方执行最小修改。
4. 在交付说明中单独列出共享文件变更。
5. 另一方在继续工作前重新读取这些文件。

依赖安装遵循以下规则：

- 前端库由 Gemini 提议和修改。
- 后端库由 Codex 提议和修改。
- 会改变构建方式或运行环境的依赖，需要项目所有者确认。
- 不做无关版本升级，不批量清理现有依赖。

## 5. API 契约流程

正式接口定义放在 `contracts/**`，说明文档放在 `docs/API_CONTRACTS.md`。一个接口至少要包含：

- 方法与路径
- 用途和权限要求
- 请求参数与请求体
- 成功响应
- 可预期错误与状态码
- 是否会修改数据
- 隐私与敏感字段说明

协作流程：

1. Gemini 提出页面需要的数据和交互场景。
2. Codex 设计接口并更新契约。
3. Gemini 基于契约接入，不依赖数据库内部结构。
4. 需要变更时优先保持向后兼容；破坏性变更必须明确标记。

## 6. Mock 数据规则

前端允许在后端完成前使用 mock，但必须满足：

- 只放在前端责任区，例如 `lib/client/mocks/**`。
- 文件顶部标记 `MOCK_ONLY`。
- 字段结构与当前契约保持一致。
- 不包含真实 API Key、账号、作品或个人信息。
- 接入正式接口后删除对应 mock，不能在生产路径静默回退到假数据。

## 7. AI 与隐私红线

- 模型 API Key 只能由服务端读取。
- 前端不得直接请求模型供应商。
- 默认不向模型发送整部作品。
- 每次 AI 请求必须由用户主动触发，并明确展示参考范围。
- AI 输出先预览，未经用户确认不得覆盖正文。
- 日志不得记录 API Key、完整正文或其他敏感内容。

## 8. Git 工作方式

建议使用独立分支：

- Codex：`codex/backend-<topic>`
- Gemini：`gemini/frontend-<topic>`

每次提交只包含本角色责任区内的改动。合并前检查：

1. 是否意外修改了另一方目录。
2. 是否修改共享文件但没有说明。
3. 接口契约是否与实现一致。
4. 是否包含密钥、构建产物或本地数据。
5. 构建与本角色负责的测试是否通过。

## 9. 冲突与例外

出现以下情况时停止修改并交给项目所有者决定：

- 同一个文件同时涉及前端与后端职责。
- 现有目录结构无法满足边界划分。
- 接口需求会明显改变产品交互。
- 需要修改另一方已经进行中的代码。
- 需要引入会影响整个项目的新框架或基础设施。

授权例外必须具体到任务和文件，单次授权不会永久改变所有权规则。
