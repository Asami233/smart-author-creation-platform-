## 3. 正式契约与兼容性

`POST /api/works/:workId/chapters/reorder`

```ts
import type { ReorderChaptersInput } from "@/contracts";

const input: ReorderChaptersInput = {
  volumeId: targetVolumeId, // UUID 或 null（未分卷）
  chapterIds: completeTargetOrder,
  expectedRevisions: completeTargetOrder.map((chapterId) => {
    const revision = confirmedChapterRevisions.get(chapterId);
    if (revision === undefined) throw new Error("目录版本不完整，请先刷新目录");
    return { chapterId, revision };
  }),
};
```

示例只展示载荷构造；变量来自前端已确认数据，错误由 UI 捕获并提示。缺少任何 revision 必须重新获取目录，不能用非空断言、固定 1 或猜测值绕过验证。

例如源卷为 `[A, B]`，目标卷为 `[C, D]`，把 A 放到 C 后面，应提交目标卷 ID 和 `[C, A, D]` 及三章的已确认版本；B 不提交且保持原排序值。同卷上移/下移也是提交该卷完整最终顺序。支持多个源卷移入同一目标卷，不支持单次为多个目标卷设置独立顺序，不提供跨作品移动。

| 行为 | 约定 |
| --- | --- |
| 目标范围 | 真实卷或 null；目标全部未删除章 + 待移入章，各一次，共 1～500 |
| 源卷 | 留下章节的顺序值可有空隙，不为补齐空隙增加无关修订 |
| 修订号 | 位置或归属实际变化的章 +1；未变的不加；旧版本保存返回 409 |
| 重复提交 | 最新版本 + 相同顺序不加修订；旧版本不自动重试 |
| 成功响应 | 200，data 为全书目录数组，不是仅目标卷；content 空字符串是摘要占位 |
| 400 | 格式/长度/重复 ID/版本覆盖不匹配 |
| 409 | 列表遗漏、失效或跨作品、版本过期、写入期间集合改变 |
| 404 / 401 | 作品不可访问/归档 / 部署环境未登录 |

**不能用返回的空 content 替换编辑器内容。** 前端合并目录元数据、修订号；实际正文需要时从章节详情获取，并保留既有草稿与迟到响应保护。

兼容性：路径及返回形状不变；`expectedRevisions` 为兼容旧调用暂时可选，但新前端必须传。旧客户端曾提交的不完整目标列表现在会 409，这是必要的数据完整性收紧。省略版本不能保护客户端过期意图；不要逐章 PATCH 绕过批量检查。

实现以物化快照冻结写入前的版本、归属和顺序，再在同一数据库语句里校验目标集合。这样自身更新的修订号不会干扰后续行校验；本地 D1 已实测。技术依据：[SQLite MATERIALIZED 说明](https://www.sqlite.org/lang_with.html#materialization_hints)。

## 4. Gemini 下一工作包

### C01：章节组织入口

- 在现有目录章节菜单加入上移、下移、“移动到…”（卷选择 + 未分卷），边界按钮禁用。
- 沿用现有分卷 UI、墨绿暖白风格、独立滚动与 `UI_STYLE_GUIDE.md`。保持当前章选中和编辑焦点；跨卷后展开目标卷，使该章可见。
- 第一批不强制拖拽，也不强制多选；如果实现拖拽，必须复用相同保存门禁和接口，并保留键盘可用的菜单入口。
- 对目标超过 500 章明确显示限制，不自动拆包提交局部列表。

### C02：保存和修订的串行保护（P0）

1. 在发送移动/排序请求前 await 已有保存队列；失败/冲突立即中止目录写请求，保留草稿。
2. 从保存完成后的权威状态构造完整列表和版本，不能捕获保存前的旧 React state。
3. 目录请求期间防止重复结构操作；与自动保存协调，避免同章并行写入。若采用短暂禁用编辑，须有明确状态且不能打断中文输入法组合过程；或排队保留新草稿，成功后用新版本保存。
4. 成功更新目录、`confirmedRevisionsRef` 等已确认版本来源；请求期间的新标题/正文不能被旧响应覆盖。响应属于旧作品/旧操作时丢弃，不能更新当前工作区。
5. 409 保留原稿，刷新目录元数据并提示重新操作，不自动重放、不调用会重置正文的全量工作区加载。
6. 断网可能意味着服务端已完成但客户端未收到响应；标记“结果待确认”，先重新读取目录再让用户决定，不盲目反向回滚或重复提交。

### C03：上一轮的少量剩余收口

- F01～F03 的主要保护已存在，不要求重写；新增移动场景必须复用并回归。
- F04：`chapter-links-dialog.tsx` 在写请求失败且事实重拉也失败后，目前只显示提示，下一次保存仍直接按旧 `serverFactsRef` 算差量。增加明确的“需要重新同步”状态；先重拉成功再计算/提交差量，保留用户期望选择。不能以不确定事实认定无变化并关闭弹窗。
- F05：`ai-settings-dialog.tsx` 预设按钮等仍为 `text-xs`（12px），而规范要求交互文字至少 14px；按钮高度 32px 不等于字号符合规范。按语义角色修正控件文字，辅助说明允许 12px，勿全站机械替换。
- 提供可访问的截图路径/附件和真实交互记录；上一交接的截图只有文件名，当前仓库未找到该凭证及其所述 `scratch/verify_apis.js`，本轮不据此宣布浏览器联合验收通过。

## 5. 联合验收清单

使用专门测试账号与样例作品，至少两作品、两卷、每卷三章；不要在真实稿件上注入网络故障。

1. 卷内上下移动、移到非空卷/空卷/未分卷，再刷新；顺序、归属、选中章正确，其他作品不变。
2. 编辑正文后立即移动；请求顺序为保存完成再排序，继续编辑不出现自身造成的旧版本 409。
3. 保存 500/409 时点移动，确认不发送排序请求，草稿可恢复。
4. 两标签同章，一个保存、另一个按旧版本排序；409 不覆稿，不部分移动。
5. 故意延迟排序响应，快速切作品或再次输入；迟到响应不串作品、不清空/覆盖新草稿。
6. 排序响应断网、刷新事实后重试；UI 不把未知结果当作成功或未执行。
7. 版本、设定关联、字数不因移动变化；TXT/DOCX/PDF 下载顺序与目录一致。后端此次新增的是 TXT 内容顺序断言，DOCX/PDF 仍需前端打开文件目视检查。
8. 关联写请求失败且重拉失败时，保留勾选；恢复网络后先同步再提交，不能误判已完成。
9. 1366×768、1440×900、1920×1080，125%/150% 缩放、键盘菜单、长目录滚动；补工作台、AI 配置和复杂弹窗截图。
