# 迭代 4 第三轮：备份冲突预检与可控恢复

日期：2026-09-27  
方向：Codex → 项目所有者  
结论：**备份恢复闭环已完成；固定使用合并副本策略，现有作品不会被覆盖、删除或自动合并。**

## 产品与页面

- 个人设置“数据保全与存储”新增“从 JSON 备份安全恢复”。
- 支持 `smart-author-backup` 文件，也支持从账号完整导出文件中提取 `content`；客户端先执行 25 MB 大小检查。
- 预检展示作品、章节、设定、历史版本和总字数，列出现有作品数、同名作品以及归档作品、回收站章节、AI 密钥缺失等警告。
- 用户必须勾选“确认为独立副本”才能恢复；页面不提供覆盖、删除或自动合并选项。
- 恢复成功展示新作品数量；同一备份重复恢复明确提示已返回上次结果，没有重复创建。

## 契约与接口

- `POST /api/backup/preflight` 接收原始 `BackupDocument`，验证结构和对象引用，返回摘要、同名冲突、警告及 30 分钟有效的签名凭据。
- 凭据绑定当前数据所有者和稳定备份内容摘要；换账号、修改备份或过期均不能恢复。
- `POST /api/backup/import` 改为接收 `{backup,previewToken,mode:"merge-copy",confirm:true}`，要求同源请求。成功返回 `importId`、新作品 ID、摘要、警告和 `alreadyImported`。
- 旧版直接提交原始备份的调用现在返回 `428 BACKUP_PREFLIGHT_REQUIRED`。这是有意的安全性破坏变更，前端和冒烟脚本已同步迁移。
- 账号完整导出仍不是直接导入格式；页面只把其中的 `content` 节点交给预检。

## 数据、迁移与恢复语义

- 新迁移 `drizzle/0004_serious_puck.sql` 增加 `backup_import_jobs`，按 `owner_id + snapshot_hash` 唯一记录恢复任务和预分配的新作品 ID。
- 同一账号对相同备份重复提交时幂等返回已完成任务；并发重复恢复返回 `409 BACKUP_IMPORT_IN_PROGRESS`。
- 任务开始前预分配所有新作品 ID。写入失败时只删除这些新作品，依赖外键级联清理卷章、设定、版本和统计，不触碰原有作品。
- 超过 5 分钟仍处于 `importing` 的任务视为中断：先精确清理预分配作品，再删除旧任务并允许重试。
- 账号永久删除流程已同步清理该账号的恢复任务记录。

## 验收证据

- 后端全量测试 **64/64**、前端全量测试 **32/32** 通过；TypeScript、涉及范围 ESLint 和生产构建通过。
- 独立 `.wrangler/account-delete-acceptance-20260927` 数据库应用迁移后完成 API 冒烟：预检 200、同名冲突 1、旧版直传 428、篡改备份 412、首次恢复 201、重复恢复 201 且 `alreadyImported:true`。
- 恢复前数据库 1 部现有作品，恢复后 2 部；新作品 ID 与源 ID、现有 ID 均不同，重复请求返回相同作品 ID，证明现有数据保留且恢复幂等。
- 生产构建的真实页面中，个人设置数据页能打开“备份预检与安全恢复”弹窗，页面明确显示先预检和合并副本语义。验收没有上传文件或写入默认数据库。
- 默认本地数据库未被本轮验收读取、修改或删除；API 冒烟仅使用隔离持久化目录。

## 兼容性与已知边界

- 备份 schema 仍为版本 1；本轮未引入覆盖恢复、选择性作品恢复或跨 schema 自动迁移。
- AI API Key 从不进入备份，因此恢复后需要重新配置。
- `backup_import_jobs` 解决同备份幂等和本轮中断补偿，不等同于多设备离线合并。
- Vinext 生产构建仍会记录既有的 RSC prefetch 兼容警告，但恢复按钮和弹窗实测可用；该警告不是本工作包新增，也未阻止页面交互。
