## 2. Codex 本轮完成的后端修复

之前 `PATCH /api/works/:workId` 带 `status: "archived"` 已写入归档，随后复用仅允许活动作品的读取函数，导致最终 404。新增回归先复现 404，再修复为正常 200。

- 更新的作品行由带 owner 和非归档状态条件的 UPDATE RETURNING 返回，以本次写入结果构造响应；不放开普通 GET 的归档访问。
- PATCH/DELETE 归档共用写入逻辑；归档与清空匹配的活动作品/章节偏好在一个 D1 batch 事务中完成。
- 不存在、他人或已归档作品的请求不写入；并发归档仅一个成功，另一个 404。
- 归档非当前作品不改当前选择，也不改其偏好更新时间。
- 不物理删除作品、章节、正文、历史版本；回收站恢复后数据保留。

### 接口与兼容性

| 接口 | 成功 | 说明 |
| --- | --- | --- |
| PATCH `/api/works/:workId` | 200，`data: { work, volumes, chapters }` | 支持原有三种 status；归档时 work.status 为 archived，可同时修改合法元数据；chapters 不含正文 |
| DELETE `/api/works/:workId` | 204，无响应体 | 现有前端归档调用保持不变 |
| POST `/api/trash/works/:workId/restore` | 沿用既有响应 | 恢复入口不变，不能通过 PATCH draft 恢复 |

普通详情、统计及章节读取对归档作品仍返回 404。重复归档仍为 404，不是幂等成功。非法参数 400，其他账号/不存在 404，部署环境未登录按原身份策略 401。

无新增字段、路由、迁移、依赖或环境变量；本次是修复成功操作误报失败，不要求 Gemini 改用 PATCH。契约注释已更新，详细说明见 `docs/API_CONTRACTS.md`。

## 3. Gemini 必修项（不由 Codex 越界修改）

### R01 / P0：目录 revision 不是正文草稿的版本基线

证据位置：`app/page.tsx` 的 `handleMoveChapter` / `handleMoveChapterToVolume`。

- 成功分支约 991、1136 行对 **全书** `updatedCatalog` 批量更新 `confirmedRevisionsRef`，但保留本地旧正文。
- 失败分支约 1033、1190 行刷新目录后也批量更新该 ref，没有将相关保存置为冲突/待确认。
- `performSave` 优先采用该 ref 的版本号，所以后续自动保存可能拿“新版本号 + 旧正文”写回，绕过乐观锁。

复现路径（代码推演，尚未浏览器执行）：A/B 两标签加载同章 r1；B 保存正文成为 r2；A 以 r1 排序收到 409；A 的 catch 拉目录后把基线改为 r2，但正文仍旧；A 再输入触发保存，提交旧稿衍生内容 + expectedRevision r2，可覆盖 B 的修改。即使排序成功，返回的无关章节若已被 B 修改，也存在同类风险。

修复要求：

1. 分开“目录观察到的服务端修订”与“当前正文草稿所基于的修订”。刷新目录只更新观察值，不默默推进草稿基线；检查 ref 和 chapter state 两个来源，不能改了 ref 却由 fallback 读取已刷新的 state。
2. 正常排序成功，仅对本次已校验目标 ID 且响应 revision 恰好等于请求 expectedRevision 加本次实际结构变化量（0/1）的章，承认自身结构更新；不得推进无关章的正文基线。若出现额外修订，按冲突处理。
3. 409 或网络结果不确定时，暂停受影响草稿自动保存，保留旧基线和本地输入；用户读取/比较正文并明确选择后才能继续。不能单纯刷新 revision 再自动存稿。
4. 目录请求等待期间排队的保存也必须经过这个冲突门禁。新建/切换/导出等调用 `flushPendingSave` 的入口不能绕过。

### R02 / P0：结构操作的互斥与迟到响应检查还不完整

证据：三个排序函数先检查 `isReorderingRef` 再 await 保存；章节函数在 await 之后才设锁，没有再次检查；分卷函数约 885 行只检查锁、不设锁，也没有 work/token 校验。恢复目录的二次请求约 1031、1188 行，await 返回后没有再次检查 token / 当前作品。

修复要求：所有结构操作使用同一生命周期管理。先取得入口互斥，再等待已有保存，期间第二次点击不能穿透；锁内捕获 workId，保存结束后再检查目标是否仍有效。不要在刷盘前注册一个让 `performSave` 等待自身的 Promise，避免循环等待。每个 await 后、所有成功/失败恢复写 state 前检查归属及代次；finally 仅清理自身锁/Promise。分卷、卷内及跨卷三个入口同样处理。

### R03 / P1：目录重同步应反映增删，且不能误报成功

当前 catch 用 `prev.map` 合并服务端目录：另一窗口新建的章不会加入，删除的章仍保留。因此遇到“目标组完整列表不匹配”后重试仍可能持续 409。目录刷新本身失败，提示仍写“已重新同步/已重新拉取”，也不准确。

修复要求：按返回的权威 ID 集合协调增删与移动；本地有未保存内容但被删除的章进入明确的草稿恢复状态，不能静默丢弃或继续保存。只有刷新成功才提示同步完成，否则保持“结果未知/目录待同步”，阻止基于旧事实的结构重试；提供显式重新同步操作。保留原稿，不通过整页刷新解决。

## 4. 必须执行的前端验收

只对临时测试作品注入故障：

1. 两标签按 R01 路径操作，A 排序冲突后继续输入，验证不会发送带 B 新修订的旧稿自动保存；比较/采纳由用户决定。
2. A 重排卷一，B 同时更新卷二某章，A 再编辑卷二，验证不会因全书目录响应而跳过正文冲突。
3. 延迟保存时连点上移/下移及分卷排序，只应有一个合法结构任务；完成后保存继续运行，没有卡住。
4. 延迟 409 后的目录重拉，切换/重新加载工作区，返回不能污染新状态；无法切换的设计需展示明确等待状态。
5. 其他窗口新增/删除目标卷章节，再重排；同步后的目录 ID 集合正确，能够在用户重新确认后恢复操作。
6. 结构请求或重同步断网：保留草稿、显示未知结果、不误报同步成功，恢复后先核对事实。
7. 继续原 G0/G1 验收，DOCX/PDF 需打开文件检查；浏览器和视觉场景未做就标记未测，不按代码存在推定通过。
